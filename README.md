## ⚖️ Юридическое предупреждение

> CourtDraft AI формирует **проект** судебного акта на основании
> предоставленных материалов. Система **не осуществляет правосудие** и
> **не принимает окончательных судебных решений**. Проект подлежит
> обязательной проверке и редактированию уполномоченным специалистом.
> Возможны ошибки и неполнота исходных данных.

Это не маркетинговая оговорка, а проектное ограничение: в коде нет пути,
который позволял бы системе утвердить решение.

## Два принципа

**Продукта:**

> ### ИИ готовит проект. Человек проверяет и принимает решение.

**Разработки:**

> ### Разрабатываем на CPU-only ноутбуке 8 ГБ. Реальная модель — на RTX 3050.

Оба принципа проверяемы. Первый — тем, что в коде нет функции
автоутверждения. Второй — тем, что вся разработка идёт на машине без
видеокарты, а перенос на мощную машину не требует правки исходников.

## Что умеет

### Каждое утверждение связано с источником

Фрагмент проекта знает, из какого документа, страницы и абзаца он
взят. В интерфейсе видно первоисточник. Если источника нет —
утверждение помечается как требующее проверки, а не додумывается.

Это центральное требование продукта. Без него генерация текста
остаётся красивым, но бесполезным для правоприменения.

### Редакция нормы подбирается по дате

Поиск статьи учитывает, какая редакция **действовала на момент
события**, а не последняя опубликованная. В запрос к индексу уходит
предикат `effective_from <= дата И НЕ effective_to < дата`.

### Поиск: смысл плюс точные совпадения

Dense-векторы находят «похожее по смыслу», но теряют точные совпадения —
номера статей, даты, суммы. Поэтому поиск двухуровневый: векторный **и**
BM25, объединённые алгоритмом Reciprocal Rank Fusion.

Объединяются не оценки (косинус и TF-IDF несопоставимы), а **ранги**.

### Проверка до человека

Автоматическая проверка ищет:

- числа, которых нет в материалах дела;
- ссылки на нормы, которых в материалах нет;
- выдуманные ФИО и состав суда;
- переставленные роли сторон — истец, назначенный плательщиком;
- утверждения без источника;
- разделы, для которых в материалах нет данных.

Результат — список замечаний с указанием места в тексте. Решение
остаётся за специалистом.

### Версии сохраняются целиком

Каждая редакция (AI → секретарь → судья) сохраняется со своим
текстом, автором и комментарием. Не diff, а полный текст: юридический
акт должен быть виден в том виде, в каком был принят.

### Слои

| Слой | Модуль | Ответственность |
|---|---|---|
| API | `app/api/routes/` | HTTP, валидация, коды ответов |
| Домен | `app/services/` | Бизнес-правила, транзакции |
| Провайдеры | `app/llm/`, `app/embeddings/` | Единственное место выбора реализации |
| Данные | `app/db/`, `app/models/` | SQLAlchemy, репозитории |
| RAG | `app/rag/` | Векторное хранилище и поиск |
| Разбор | `app/ingestion/` | Извлечение текста и структурный чанкинг |

### Правило, которое держит проект

**Бизнес-логика не знает о конкретной модели.** Агенты работают только
через интерфейсы:

```python
class LLMProvider(Protocol):
    async def generate(self, request: LLMRequest) -> LLMResponse: ...
    async def generate_json(self, request: LLMRequest, *, default=None) -> dict: ...
    async def health(self) -> bool: ...
```

Реализации — `MockLLMProvider` и `OllamaProvider`. Переключение режима
происходит только через `.env` и **не требует правки агентов**. Нарушение
этого правила превратит перенос на RTX 3050 в переписывание кода.

Проверяется тестом: обе реализации должны удовлетворять одному протоколу.

## Режимы: разработка и запуск

Различие между машинами — **только в `.env`**. Код одинаковый.

```env
# ── Ноутбук 8 ГБ, без GPU ──────────────────────────────
LLM_PROVIDER=mock
EMBEDDING_PROVIDER=mock
OLLAMA_ENABLED=false
APP_ENV=development
DATABASE_URL=
QDRANT_MODE=memory

# ── Компьютер с RTX 3050 ───────────────────────────────
LLM_PROVIDER=ollama
EMBEDDING_PROVIDER=local
OLLAMA_ENABLED=true
OLLAMA_MODEL=qwen3.5:4b
APP_ENV=runtime
DATABASE_URL=postgresql+asyncpg://courtdraft:courtdraft@localhost:5432/courtdraft
QDRANT_MODE=server
```

### Почему база данных умеет работать без PostgreSQL

PostgreSQL на ноутбуке разработки установить нельзя: Docker
недоступен, на системном диске 1,2 ГБ. Слой данных сделан переносимым —
ничего PostgreSQL-специфичного в моделях нет:

| Вместо | Используется | Почему |
|---|---|---|
| `SERIAL` | `Uuid` | работает и на PostgreSQL, и на SQLite |
| `JSONB` | `JSON` | `JSONB` есть только у PostgreSQL |
| нативный `ENUM` | `String` + валидация Pydantic | `ENUM` в PostgreSQL требует миграции на каждое новое значение |
| `TIMESTAMP` без зоны | `DateTime(timezone=True)` | сравнение дат действия нормы |

Расхождения диалектов, которые ломают тихо, закрыты явно и покрыты
тестами: точность времени, внешние ключи, batch-режим миграций.

## Веб-интерфейс

Интерфейс раздаётся тем же приложением, что и API, — на `/app`.

```powershell
.\scripts\start.ps1
```

Откройте <http://localhost:8000/> — корень сразу ведёт на интерфейс.

Что можно сделать, не написав ни строки кода:

1. нажать **«Создать демо-дело»** — дело создаётся, в него загружаются
   шесть синтетических материалов;
2. нажать **«Сформировать проект»** — запускается фоновая задача,
   интерфейс опрашивает её состояние и показывает движение;
3. прочитать проект по разделам; разделы, которые не удалось подтвердить
   по материалам дела, выделены жёлтым и помечены «требует проверки»;
4. посмотреть, какие факты и из каких документов построен каждый раздел;
5. посмотреть замечания проверки с указанием места в тексте;
6. внести правку — она сохраняется отдельной версией, предыдущая остаётся.

Никакой сборки: обычные HTML, CSS и JavaScript, без npm. Для страницы на
один экран сборщик — лишняя зависимость и лишний день настройки.

**Честное предупреждение встроено в интерфейс.** Шапка, каждый ответ API и
каждый блок с текстом акта сопровождаются пометкой «Это проект, а не решение
суда». В режиме заглушки ни один раздел не остаётся без пометки
«требует проверки»: настоящая модель не вызывалась, и проверять было нечего.

### Проверка контракта интерфейса

У интерфейса нет браузерных тестов, но есть контракт — последовательность
вызовов API. Скрипт повторяет её ровно так, как делает страница, и падает
на первом несовпадении.

```powershell
.\backend\scripts\check_ui.ps1
```

Скрипт поднимает сервис на свободном порту с **отдельной временной базой**,
прогоняет 13 шагов и гасит сервис. Рабочая база не трогается: иначе в
списке дел накапливались бы тестовые производства.

### Сквозной прогон через HTTP

```powershell
cd backend

# мгновенно, на заглушке
.venv\Scripts\python.exe scripts\e2e_http.py --provider mock

# настоящая модель, около трёх минут
.venv\Scripts\python.exe scripts\e2e_http.py --provider ollama
```

Что он проверяет:

1. дело создаётся через `POST /api/cases`;
2. шесть документов загружаются через `POST /api/cases/{id}/documents`;
3. проект формируется **в фоне** — формирование занимает минуты, поэтому
   эндпоинт возвращает `202` и `job_id`, а не готовый текст;
4. проект читается из базы: 5 разделов, 46 фактов со ссылками на источники;
5. результат проверки сохраняется вместе с проектом;
6. правка судьи сохраняется как **вторая версия**, а первая остаётся
   нетронутой — каждая редакция хранится целиком (п.31).

Последний прогон на настоящей модели: 197 секунд, 5 разделов,
проверка `REVIEW_REQUIRED`, 12 замечаний.

### Что показывает демо про качестве

Модель на 1.5B параметров **пишет слабо** — она путает роли сторон,
повторяется, иногда выдаёт бессвязицу. Это честное ограничение малой
модели на процессоре, а не дефект конвейера.

Но проверка работает. Она ловит то, что модель выдумала или перепутала:

- суммы, которых нет в материалах дела;
- ссылки на нормы, отсутствующие в материалах;
- выдуманные ФИО — «Судья: Иванов Иван Иванович» такого в деле нет;
- выдуманный состав суда, в том числе прокурора, который в состав суда
  не входит;
- переставленные роли сторон — «истец обязан уплатить» вместо взыскания
  в его пользу;
- разделы, оборванные лимитом ответа.

Каждое за��ечание указывает место в тексте и раздел. Проверка сама по
себе ничего не решает: решение принимает человек.

Поэтому демо и ценно: оно показывает, что система **замечает** выдумки
модели, а не принимает их за факты. На RTX 3050 с `qwen3.5:4b` качество
текста будет заметно выше, а проверка останется.

### Чего проверка пока не ловит

Честное ограничение, найденное на реальных прогонах:

- **Почти повторяющиеся пункты резолютивной части.** Пункты 2–9 отличаются
  только номером — это разворот текста, а не повтор строки, поэтому
  дедупликация их не снимает.
- **Смысловые ошибки при верных ссылках.** Если модель правильно сослалась
  на норму и правильно назвала сумму, но неверно истолковала обстоятельства,
  регулярные проверки это не увидят: для этого нужен разбор смысла.

Правила проверки персон и ролей — в `backend/app/verification/persons.py`,
с границами применимости описаны в начале модуля.

Команда пересобирает демо-дело и открывает интерфейс на нём: <http://localhost:8000/>.

Если модель не подключена, интерфейс честно сообщает об этом баннером, а
разделы помечает «заглушка». Резолютивная часть от модели не зависит:
она собирается правилами.

### Демо на сайте

```powershell
python scripts\build_demo_site.py          # собрать site/demo/
python scripts\check_site.py               # проверить вёрстку и ссылки
```

Демо на сайте — **запись того же прогона**: `scripts/build_demo_site.py`
берёт `data/demo/output/result.json` и собирает из него статическую
страницу, которая работает без сервера и без модели. Собирать руками
нельзя: написанное вручную демо через месяц перестаёт совпадать с
продуктом, и на встрече выясняется, что показывали не то.

Скрипт отказывается собирать страницу, если в данных нет маркера
синтетичности. Материалы дел не должны покидать машину, и публикация
на публичном сайте — самая опасная точка для этой ошибки.

Публикация: `.github/workflows/pages.yml` отдаёт наружу только каталог
`site/`. Перед публикацией прогоняются проверка вёрстки и проверка
синтетичности данных.

### Резолютивная часть собирается правилами

Раздел «РЕШИЛ» **не генерируется моделью** — он собирается из
предъявленных требований по жёсткой грамматике. Причина не в
эстетике: это единственная часть решения, где ошибка непоправима.
В мотивировке ошибка — вопрос к специалисту, здесь — отмена решения.
Модель на 1,5B путает стороны именно тут, и лечится это не длиной
промпта, а структурой.

Правила выведены из **1 425 гражданских решений** (датасет
`TryDotAtwo/russian-legal-ner`, разбор воспроизводится скриптом
`scripts/extract_rules.py`). Что из этого выяснилось:

| Что было у нас | Как пишет суд | Документов |
|---|---|---|
| ст. 209–211 ГПК РФ как основание | **ст. 198 ГПК РФ** | 209–211 нет ни разу |
| «истец» и «ответчик» | ФИО и организации | 680 против 358 |
| «00 коп.» | `5034 руб. 79 коп.` | 613 |
| итога нет | `а всего 5467 (…) руб.` | 189 |
| заочного производства нет | 1-й пункт резолюции | **698 (49 %)** |
| пошлина «в пользу истца» | «в доход бюджета» | 98 (6,9 %) |

**Пошлина взыскивалась не в тот адресат.** Код предписывал вернуть
госпошлину истцу. По ст. 98 ГПК РФ она возвращается бюджету: истец
её не платил, её уплатил бюджет, и возврата истцу закон не
предусматривает. Теперь адресат бюджета берётся из материалов, а при
отсутствии остаётся видимая пометка. Иные расходы (ст. 100 ГПК РФ)
возвращаются истцу — их нёс он сам.

**Основание решения было неверным.** Ст. 209–211 ГПК РФ стояли в
шаблоне без проверки; разбор настоящих решений это опроверг — в
резолюциях они не встречаются ни разу. Заменены на ст. 198.

**Заочное производство — половина дел**, а кода для него не было.
Теперь система различает три режима: обычный, заочный
(с правом ответчика на отмену за 7 дней и особым сроком обжалования)
и неявку истца (ст. 167 ГПК РФ). Порядок определяется по материалам
дела, а не по умолчанию.

Полностью: `docs/real-resolutions-rules.md`.

### Честно о проверке качества

Раньше здесь стояло: «метрики идеальны, но смысла не проверяют, на
перефразированных запросах ноль». **Половина этого была неправдой, и
правда была хуже.**

Обе прежние цифры получались из-за бага в самих скриптах оценки:
ключи корпуса были `c0`, `c1`, а магазин берёт `case_id` из `chunk_id`
формата `<case_id>:<index>`. Без двоеточия фильтр отсекал **все**
векторы. Плотный поиск молчал всегда, независимо от модели:

- `1.000` на дословных запросах давал только BM25, эмбеддинги в нём
  не участвовали;
- `0.000` на перефразированных давал не «заглушка», а пустой выдача:
  ни BM25, ни плотный поиск ничего не возвращали.

После исправления, на настоящей модели `bge-m3`:

| Метрика | Значение |
|---|---|
| Recall@5 на перефразированных запросах | **1.000** |
| Правильный ответ **первым** (top-1) | **1.000** из 5 |
| BM25 на тех же запросах | **ничего** |

Последняя строка и есть главное: там, где поиск по словам бессилен,
поиск по смыслу ставит верный фрагмент первым.

**Чего эти цифры не доказывают.** Корпус — 6 фрагментов, запросов — 5.
Recall@5 на таком наборе почти гарантирован, поэтому в отчёте выводится
порядок ответа, а не только попадание. Для настоящих метрик нужен
корпус реальных дел.

Проверить у себя:

```powershell
cd backend
.venv\Scripts\python.exe scripts\eval_sanity.py      # смысл
.venv\Scripts\python.exe scripts\eval_retrieval.py   # индексация
.venv\Scripts\python.exe scripts\check_embeddings.py # модель отвечает
```

## Ограничения

Система **не готова к работе с реальными судебными делами**:

- нет аутентификации и разграничения доступа;
- нет шифрования данных на диске;
- нет журнала аудита действий пользователя;
- обезличивание персональных данных основано на регулярных выражениях —
  это не защита уровня production;
- нормативная база и судебная практика пока **синтетические**;
- интерфейс в разработке, основная работа — через API.

**Не выставляйте систему в сеть.**

### Что сознательно не входит в MVP

Обучение моделей (LoRA/QLoRA), Kubernetes, распределённый инференс,
облачные LLM, автоматическое утверждение решений, массовый сбор
судебных практик, сложная ролевая модель доступа.

## Безопасность данных

**Гарантируется:**

- работа только на вашей машине;
- никаких облачных LLM и embedding API;
- материалы дел не покидают компьютер;
- материалы дел не попадают в систему контроля версий;
- система не публикует и не утверждает судебные акты.

Подробности: [`SECURITY.md`](SECURITY.md)

## Минисайт

В каталоге [`site/`](site/) — статический сайт «Помощник судьи» для
GitHub Pages. Работает офлайн, без сборки и внешних зависимостей.

Привязка к бэкенду подготовлена в [`site/assets/api.js`](site/assets/api.js):
достаточно указать адрес API. Сейчас сайт статичен намеренно — разметка
не зависит от данных, чтобы страница работала на Pages без сервера.

Включение Pages: **Settings → Pages → Source: Deploy from a branch →
`main`, папка `/site`**.

## Проверка качества кода

```powershell
cd backend
.venv\Scripts\python.exe -m pytest              # тесты
.venv\Scripts\ruff.exe check app tests scripts  # линтер
.venv\Scripts\mypy.exe app                      # типы (strict)
```

Требование к фазам: после каждой фазы прогоняются тесты, линтер и
проверка типов. Незавершённая функция не остаётся как `TODO` или `pass`.
