# API CourtDraft AI

Базовый адрес при локальном запуске: `http://localhost:8000`

Интерактивная документация: <http://localhost:8000/docs>
Схема OpenAPI: <http://localhost:8000/openapi.json>

---

## Общие правила

**Аутентификации нет.** Система рассчитана на запуск на локальной машине
одного пользователя. Выставление в сеть без реализации контроля доступа
недопустимо.

**Формат ошибок** — стандартный FastAPI:

```json
{ "detail": "Дело не найдено" }
```

**Коды ответов:**

| Код | Значение |
|---|---|
| `200` | успех |
| `201` | создан объект |
| `404` | объект не найден |
| `409` | конфликт: дубликат номера дела или документа |
| `422` | ошибка валидации входных данных
| `202` | задача принята в фоновый режим | |
| `503` | недоступен обязательный компонент (например, база данных) |

## Системные эндпоинты

### `GET /api/health`

Состояние всех компонентов. **Всегда отвечает `200`** с полным отчётом:
клиенту нужно видеть, что именно не работает.

Ключевое разделение — `required`. На ноутбуке разработки отсутствие
Ollama и GPU это `NOT REQUIRED`, на машине с RTX 3050 тот же компонент
станет `UNAVAILABLE` с `required: true`.

```json
{
  "status": "OK",
  "version": "0.1.0",
  "environment": "development",
  "components": [
    {
      "name": "Database",
      "state": "OK",
      "detail": "SQLite (MOCK-режим): sqlite:/D:/courtdraft-ai/data/cases/courtdraft.db",
      "required": true
    },
    {
      "name": "LLM",
      "state": "MOCK",
      "detail": "MockLLMProvider (реальная модель не вызывается)",
      "required": false
    },
    {
      "name": "Ollama",
      "state": "NOT_REQUIRED",
      "detail": "не требуется в режиме разработки",
      "required": false
    },
    {
      "name": "GPU",
      "state": "NOT_REQUIRED",
      "detail": "режим разработки, GPU не требуется",
      "required": false
    }
  ],
  "summary": {
    "Backend": "OK",
    "Database": "OK",
    "LLM": "MOCK",
    "Ollama": "NOT_REQUIRED",
    "GPU": "NOT_REQUIRED"
  },
  "warnings": []
}
```

Состояния компонента:

| Состояние | Значение |
|---|---|
| `OK` | работает |
| `MOCK` | работает в режиме заглушки — штатно на DEV-машине |
| `NOT_REQUIRED` | не нужно в текущем режиме |
| `UNAVAILABLE` | нужно, но отсутствует |
| `ERROR` | ошибка соединения |

Итоговый `status`: `OK` · `DEGRADED` · `ERROR`.

### `GET /api/info`

Идентификация сервиса и текущий режим. Содержит юридическое
предупреждение (п.70 ТЗ).

```json
{
  "name": "CourtDraft AI",
  "version": "0.1.0",
  "environment": "development",
  "llm_provider": "mock",
  "embedding_provider": "mock",
  "ollama_enabled": false,
  "disclaimer": "CourtDraft AI формирует проект судебного акта..."
}
```

### `GET /api/ready`

Для оркестратора. Возвращает `503`, только если сломан обязательный
компонент. Отсутствие Ollama в режиме разработки поводом отказать
в готовности не является.

## Дела

### `POST /api/cases`

Создать дело.

```json
{
  "case_number": "DEMO-001",
  "court_name": "Демо районный суд",
  "case_type": "civil",
  "category": "взыскание",
  "is_synthetic": true
}
```

| Поле | Обязательное | Описание |
|---|---|---|
| `case_number` | да | Номер дела. Уникален. |
| `court_name` | да | Наименование суда |
| `case_type` | да | Тип дела |
| `category` | нет | Категория |
| `is_synthetic` | нет | Помечает данные как синтетические. **Для демо обязательно `true`** |

Ответ `201`:

```json
{
  "id": "b1f4d0e2-...",
  "case_number": "DEMO-001",
  "status": "NEW",
  "is_synthetic": true,
  "participants": [],
  "documents": [],
  "document_count": 0,
  "created_at": "2026-10-08T10:00:00Z"
}
```

Ошибки: `409` — дело с таким номером уже существует; `422` — ошибка
валидации, в том числе **при неизвестном поле** (`extra: forbid` —
опечатка должна быть видна, а не проигнорирована).

### `GET /api/cases`

Список дел.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `status` | — | Фильтр по статусу |
| `limit` | `50` | 1–200 |
| `offset` | `0` | Смещение |

```json
{ "items": [ ... ], "total": 42 }
```

`total` соответствует применённому фильтру, а не общему числу дел.

### `GET /api/cases/{case_id}` — одно дело, `404` если не найдено.

### `PATCH /api/cases/{case_id}`

```json
{ "status": "UNDER_REVIEW" }
{ "category": "договорные споры" }
```

Статусы дела:

```
NEW → PROCESSING → DRAFT_READY → UNDER_REVIEW
    → CORRECTED → READY_FOR_APPROVAL → ARCHIVED
```

## Документы дела

### `POST /api/cases/{case_id}/documents`

Зарегистрировать документ.

```json
{
  "filename": "01_claim.pdf",
  "document_type": "CLAIM",
  "mime_type": "application/pdf",
  "page_count": 3,
  "text": "Исковое заявление о взыскании..."
}
```

Типы документов **расширяемы**: поле `document_type` принимает любое
значение. В ответе поле `is_known_type` покажет, входит ли оно в базовый
перечень.

| Тип | Значение |
|---|---|
| Иск | `CLAIM` |
| Отзыв | `RESPONSE` |
| Договор | `CONTRACT` |
| Платёжный документ | `RECEIPT` |
| Акт | `ACT` |
| Заключение эксперта | `EXPERT_OPINION` |
| Доказательство | `EVIDENCE` |
| Ходатайство | `MOTION` |
| Протокол | `PROTOCOL` |
| Прочее | `OTHER` |

`409` — документ с таким SHA256 уже загружен (защита от дублей).

### `GET /api/cases/{case_id}/documents`

Параметр `type` фильтрует по типу документа.

## Проект решения (Фаза 11)

### `POST /api/cases/{case_id}/draft` — сформировать проект

```json
{ "template_name": "civil_judgment", "actor": "judge" }
```

**По умолчанию возвращает `202` и `job_id`, а не сам проект.** Формирование
на процессоре занимает две-полторы минуты; синхронный ответ невозможен —
соединение оборвалось бы по таймауту, и клиент счёл бы сервис зависшим.

Ответ `202`:

```json
{
  "job_id": "…",
  "case_id": "…",
  "status": "PENDING",
  "is_draft": true,
  "disclaimer": "Это проект, а не решение суда…"
}
```

Параметр `?wait=true` заставляет ждать и вернуть готовый проект. Применять
только там, где клиент заведомо готов ждать: автоматические проверки,
импорт данных, сценарии проверки качества.

`409` — в деле нет документов: составлять проект по пустому делу нельзя.

### `GET /api/jobs/{job_id}` — состояние фоновой задачи

```json
{
  "job_id": "…", "case_id": "…",
  "state": "PENDING | RUNNING | DONE | FAILED",
  "created_at": "…", "started_at": "…", "finished_at": "…",
  "error": "", "draft_id": "…", "version": 1, "verification": "REVIEW_REQUIRED"
}
```

**Ограничение, о котором нужно знать:** задачи хранятся в памяти процесса.
Перезапуск сервера теряет незавершённые задачи, а при нескольких рабочих
процессах задача, принятая одним, не видна другому. Для одного процесса
это приемлемо; для промышленного развёртывания нужен брокер задач.

### `GET /api/cases/{case_id}/draft` — последняя версия проекта

Возвращает текст, разбивку по разделам, источники и результат проверки.
Если проекта ещё нет — `200` с `null`: клиенту нужно отличать «проекта нет»
от «дела нет» (второй случай даёт `404`).

```json
{
  "id": "…", "case_id": "…",
  "status": "DRAFT", "current_version": 1,
  "text": "…",
  "sections": [
    { "key": "operative", "name": "РЕШИЛ", "text": "…",
      "needs_review": true, "citations": ["01_claim.txt"], "is_mock": false }
  ],
  "sources": ["01_claim.txt", "03_contract.txt"],
  "verification": {
    "status": "REVIEW_REQUIRED",
    "issues": [
      { "type": "LAW_NOT_FOUND", "severity": "HIGH",
        "section": "Мотивировочная часть",
        "reason": "ссылка на ст. 314 ГК не подтверждена материалами дела" }
    ],
    "claims_checked": 5, "unsupported_claims": 3, "sections_checked": 5
  },
  "is_draft": true,
  "disclaimer": "Это проект, а не решение суда…"
}
```

### `GET /api/cases/{case_id}/draft/versions` — все версии

Каждая редакция хранится **целиком** со своим автором: судебный акт нужно
уметь показать в том виде, в каком он был принят, поэтому сохраняется полный
текст, а не разметка изменений.

### `POST /api/drafts/{draft_id}/versions` — сохранить правку человека

```json
{ "text": "полный текст акта", "author": "judge", "comment": "исправлена резолютивная часть" }
```

`author` допускает только `secretary` или `judge`. Правка от имени машины
через эту ручку невозможна: иначе в истории проекта появились бы записи
от модели и вопрос «кто подписал акт» потерял бы смысл.

### `GET /api/cases/{case_id}/evidence` — пакет доказательств

Факты со ссылкой на источник. Отдаётся вместе с проектом, чтобы интерфейс
мог показать, из каких документов построен каждый раздел.

### `PATCH /api/drafts/{draft_id}/status` — смена статуса проекта

## Демонстрационное дело

### `GET /api/demo/manifest` — описание синтетического дела

Ответ помечен как синтетический: интерфейс показывает пометку пользователю,
а не прячет её в коде страницы.

### `GET /api/demo/{filename}` — текст демонстрационного документа

Имя файла сверяется со списком из манифеста, а не принимается как есть:
иначе через эту ручку можно было бы прочитать любой файл на диске, указав
вместо имени `../../.env`. Ответ помечен заголовком `X-Synthetic-Data: true`.

## Веб-интерфейс

Интерфейс раздаётся тем же приложением по пути `/app`. Корень `/`
перенаправляет на него, а `/api` отдаёт адреса.

| Адрес | Что |
|---|---|
| `/` | перенаправление на `/app` |
| `/app` | интерфейс помощника судьи |
| `/docs` | интерактивная документация API |
| `/api` | адреса сервиса в виде JSON |

Приложение работает и без интерфейса: если каталог `frontend/` пуст, корень
отдаёт JSON со ссылками на документацию, а `/api` не упоминает `/app`.
Отсутствие файлов интерфейса — не повод считать установку сломанной.

### Проверка готовности и схемы

`GET /api/ready` возвращает `503`, если схема базы отстаёт от моделей, и
показывает, каких колонок не хватает, вместе с командой исправления.

Это сделано потому, что `create_all` только создаёт таблицы и никогда не
меняет существующие: база, созданная до появления нового поля, продолжает
работать и падает позже внутри фоновой задачи сообщением
`no column named ...`, которое ничего не объясняет.

## Названия эндпоинтов отличаются от ТЗ

ТЗ перечисляет четыре ручки под именами `analyze`, `analysis`, `revise`,
`sources`. В коде они реализованы — все четыре, с проверенными путями и
поведением, — но называются иначе:

| Из ТЗ | Фактический эндпоинт | Что делает |
|---|---|---|
| `POST /api/cases/{id}/analyze` | `POST /api/cases/{case_id}/draft` | Сформировать проект акта. Возвращает `202` и `job_id`: генерация занимает минуты. С `?wait=true` ждёт результата — только для автоматических проверок |
| `GET /api/cases/{id}/analysis` | `GET /api/cases/{case_id}/draft` | Последняя версия проекта вместе с проверкой. `null`, если проекта ещё нет |
| `POST /api/drafts/{id}/revise` | `POST /api/drafts/{draft_id}/versions` | Сохранить правку человека как новую версию. Текст приходит целиком: разметка изменений для судебного акта недостаточна |
| `GET /api/drafts/{id}/sources` | `GET /api/cases/{case_id}/evidence` | Пакет доказательств: из каких документов построен каждый раздел. Принимает `category` и `limit` (1–500) |

Раздел «5b. Пакет доказательств, проект и проверка (Фазы 8–10)» в
`architecture.md` описывает именно их.

Раньше здесь стояла таблица «перечислены в ТЗ, но ещё не сделаны». Она была
неверной: проверка по коду (`app/api/routes/drafts.py`) показала, что все
четыре функции реализованы, просто под другими именами. Клиенту, который
искал `analyze`, это объявление сообщало «функции нет» — и он уходил искать
существующую, не находя.

Если контракт ТЗ обязателен для внешнего клиента, нужны алиасы-роуты.
Пока их нет — используйте фактические имена выше.

## Пример полного цикла (MOCK-режим)

```powershell
$api = "http://localhost:8000"

# 1. Создать дело
curl.exe -s -X POST "$api/api/cases" -H "Content-Type: application/json" `
  -d '{\"case_number\":\"DEMO-001\",\"court_name\":\"Демо суд\",\"case_type\":\"civil\",\"is_synthetic\":true}'

# 2. Добавить документ
curl.exe -s -X POST "$api/api/cases/<ID>/documents" -H "Content-Type: application/json" `
  -d '{\"filename\":\"01_claim.pdf\",\"document_type\":\"CLAIM\",\"text\":\"Исковое заявление\"}'

# 3. Проверить состояние
curl.exe -s "$api/api/health"
```

## Полный цикл до проекта

Формирование проекта проверяется сквозным сценарием: он создаёт дело,
загружает материалы, запускает генерацию через фоновую задачу, читает
результат из базы и проверяет, что версии сохраняются целиком.

```powershell
cd D:\courtdraft-ai\backend

# мгновенно, на заглушке
.venv\Scripts\python.exe scripts\e2e_http.py --provider mock

# настоящая модель, около трёх минут
.venv\Scripts\python.exe scripts\e2e_http.py --provider ollama
```

> **Примечание для разработки.** На этой машине `curl.exe` и
> `Invoke-WebRequest` падают с `SEC_E_INTERNAL_ERROR 0x80090304`
> (проблема сетевого стека Windows). Скрипты проекта выполняют
> HTTP-запросы через Python — `.\scripts\health.ps1` работает корректно.
