# Отчёт: CourtDraft AI — состояние и план до MVP

**Дата:** 8 октября 2026
**Репозиторий:** `D:\courtdraft-ai` — 7 коммитов, 96 файлов, дерево чистое
**Проверки:** 248 тестов проходят, `ruff` чист, `mypy --strict` чист по 41 файлу

---

## 1. Итог в одном абзаце

Работающий конвейер есть: материалы дела разбираются, индекс ищется, собирается
пакет доказательств, настоящая локальная модель пишет проект решения по пяти
разделам, проверка сверяет текст с материалами. Всё это запускается одной
командой на ноутбуке без видеокарты.

**Но это скрипт, а не продукт.** Проект нельзя получить через HTTP, он не
сохраняется в базу, нет интерфейса. Судья не может этим пользоваться — только
разработчик в командной строке. До MVP не хватает именно этого слоя, а не
интеллекта: алгоритмы уже на месте и работают.

## 3. Честная оценка качества

### 3.1 Модель на 1.5B параметрах пишет слабо

На последнем прогоне:

**Вводная часть** — выдумала состав суда: «Судья: Иванов Иван Иванович»,
«Состав суда: прокурор, судья, секретарь». В материалах этого нет.

**УСТАНОВИЛ** — превратила разделы иска «ОБСТОЯТЕЛЬСТВА» и «ПРАВОВЫЕ ОСНОВАНИЯ»
в «пункты 1.1.1 и 1.1.2 договора».

**РЕШИЛ** — развернула один пункт в девять почти одинаковых и перепутала
роли сторон: истец должен **получить** деньги, а в тексте он их **платит**.

### 3.2 Проверка это не ловит

| Выдумка | Ловит? |
|---|---|
| Число, которого нет в материалах | да |
| Ссылка на норму, которой нет в материалах | да |
| Раздел без данных в материалах | да |
| Выдуманное ФИО судьи | **нет** |
| Перепутанные роли сторон | **нет** |
| Пункты, отличающиеся только номером | **нет** |

Это ограничение зафиксировано в коде, README и `architecture.md` — не спрятано.

### 3.3 Что из этого следует

Проверку надо расширять сверкой персон и ролей со списком участников дела.
А резолютивную часть вообще нужно отдавать правилам, а не модели: в модели
ошибки — 90% качества, и на 1.5B они не лечатся промптом.

## 4. Что мешает MVP — один главный разрыв

**Всё написанное работает как скрипт.** Разрыв не в алгоритмах, а в слое
доступа.

Конкретно:

| Что | Факт |
|---|---|
| Эндпоинтов генерации проекта | **нет** — есть только дела, документы, участники |
| Эндпоинта проверки | **нет** |
| Эндпоинта поиска по материалам | **нет** |
| `DraftRepository` | написан, но **нигде не вызывается** |
| Таблицы `drafts`, `draft_versions`, `verifications`, `evidence_items` | созданы, но **кто-то не пишет** в них |
| Веб-интерфейс | пустой каталог `frontend/` |
| Модуль MCP | пустой |
| Авторизация | нет |

То есть проект решения существует только в памяти во время работы скрипта.
Сохраняется он как файл `draft.md`. Версий, истории правок, проверок в базе
нет — а без них продукт не выполняет главное требование: каждая редакция
сохраняется со своим текстом и автором.

## 5. План до MVP на следующей неделе

Оценка: 5 рабочих дней. Порядок жёсткий — каждый день зависит от предыдущего.

### Понедельник — сохранение проекта в базу

Без этого всё остальное бессмысленно: показывать нечего.

- `DraftService`: создание проекта, сохранение в `drafts`, версия в
  `draft_versions`, результат проверки в `verifications`, факты в
  `evidence_items`.
- Каждая редакция сохраняется целиком со своим автором — «AI», «секретарь»,
  «судья». Не разметка правок, а полный текст: юридический акт должен быть
  виден в том виде, в каком был принят.
- Готово, когда: скрипт демо пишет проект в PostgreSQL и его видно в
  `SELECT * FROM draft_versions`.

### Вторник — HTTP-доступ

- `POST /api/cases/{id}/draft` — сформировать проект.
- `GET  /api/cases/{id}/drafts` — список версий.
- `POST /api/drafts/{id}/verify` — проверить, вернуть замечания.
- `POST /api/cases/{id}/search` — поиск по материалам с источниками.
- Асинхронность обязательна: генерация занимает 140 секунд, синхронный
  эндпоинт отвалится по таймауту. Нужен фоновой job и опрос статуса.
- Готово, когда: `curl` создаёт проект и возвращает его текст.

### Среда — настоящие эмбеддинги

Сейчас в демо `MockEmbeddingProvider`. Поиск работает только на совпадении
слов; на пересказе запроса он уже даёт Recall@5 = 0.00.

- Проверено: `nomic-embed-text:v1.5` существует, 274 МБ, 2K контекст,
  работает на процессоре. Это разблокирует настоящий поиск на этом ноутбуке.
- Внимание: размерность 768, а в демо стоит 1024. Менять надо в настройках
  и в индексе, иначе Qdrant откажется принимать векторы.
- На RTX 3050 — `bge-m3`, там 1024 измерения и заметно лучше качество.
- Готово, когда: `EMBEDDING_PROVIDER=ollama`, поиск находит документ по
  пересказу, а не по совпадению слов.

### Четверг — веб-интерфейс

Одна страница, без сборки и без npm — чтобы не тратить день на настройку.

- Выбрать дело.
- Показать список материалов.
- Кнопка «Сформировать проект», индикатор выполнения.
- Показать проект по разделам; каждый фрагмент с пометкой
  `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ` подсвечен.
- Список замечаний проверки с указанием места в тексте.
- Готово, когда: судья открывает страницу, загружает дело, получает проект
  и видит, что именно надо проверить.

### Пятница — расширение проверки и приёмка

- Сверка ФИО и должностей со списком участников дела — ловит «Иванов Иван
  Иванович», которого нет в материалах.
- Сверка ролей сторон: «истец» не должен быть плательщиком по резолютивной
  части.
- Прогон на RTX 3050 с `qwen3.5:4b`, сравнение качества.
- Приёмка по критериям ниже.

### Что сознательно не делаем на этой неделе

- MCP-сервер — не нужен для MVP, только для интеграции с внешними системами.
- Полноценная редактура с отслеживанием правок — версии целиком достаточно.
- Анализ дела отдельным агентом — пакет доказательств покрывает MVP.
- Реальные эмбеддинги `bge-m3` — требуют видеокарты, проверяем на RTX 3050.
- Аутентификация — для внутреннего демо достаточно; на внешний контур
  обязательна отдельным этапом.

## 6. Критерии готовности MVP

MVP готов, если одновременно верно всё перечисленное.

1. Судья открывает веб-страницу, выбирает дело и видит его материалы.
2. Нажимает «Сформировать проект» и через две-три минуты получает текст
   решения по пяти разделам.
3. Каждый раздел показывает, из каких материалов он построен.
4. Каждое утверждение без источника помечено `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`.
5. Проверка показывает список замечаний с указанием места в тексте.
6. Проект сохранён в базе вместе с результатом проверки.
7. Вторая редакция сохраняется отдельной версией и не затирает первую.
8. Проект **не является решением суда** — это видно на экране явно.
9. Ничего не уходит в интернет: все данные и модели локальные.
10. 248 тестов проходят, `ruff` и `mypy --strict` чисты.

## 7. Риски и блокеры

| Риск | Влияние | Что делать |
|---|---|---|
| **Залив на GitHub невозможен** | нет удалённого репозитория, `gh`, токена и помощника авторизации | создать пустой репозиторий и один раз авторизоваться через GitHub Desktop |
| Качество текста на 1.5B | резолютивная часть непригодна | резолютивную часть строить правилами, а не моделью |
| Генерация 140 с на CPU | интерфейс «висит» | фоновый job, опрос статуса, обязательно со вторника |
| Свободно 1–1.5 ГБ RAM | риск падения при загрузке модели | держать `OLLAMA_KEEP_ALIVE`, не запускать параллельно тяжёлое |
| Проверка не ловит выдуманные ФИО и роли | риск принять неверный текст за годный | расширить проверку в пятницу |
| Метрики поиска не измерены честно | `Recall@5 = 1.000` врёт: запросы почти дословно совпадают с корпусом | после эмбеддингов прогнать `eval_sanity.py` и записать честные числа |
| Никакой авторизации | любой может читать дела | обязательно до любого внешнего доступа |

## 8. Что нужно от человека

| Вопрос | Почему блокирует |
|---|---|
| URL репозитория и разовая авторизация | без этого код не уходит с машины и теряется при поломке диска |
| Доступ к машине с RTX 3050 | без неё не проверить `qwen3.5:4b` и `bge-m3`, а это половина заявленного качества |
| Второй корпус реальных материалов дела | на одном синтетическом деле метрики бесполезны — это главное ограничение проверки качества |
| Решение по резолютивной части: правила или модель | меняет архитектуру, лучше решить до среды |
