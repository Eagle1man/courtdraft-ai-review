# Архитектура CourtDraft AI

Версия 0.1 · Фазы 1–2 выполнены

## 1. Зачем разделение MOCK / REAL

Машина разработки — 8 GB RAM, без GPU. Реальная модель там не запустится.
Но продукт должен проверяться целиком, включая пайплайн.

Решение: единственный переключатель в `.env`.

```
LLM_PROVIDER=mock   ->  MockLLMProvider
LLM_PROVIDER=ollama ->  OllamaProvider
```

Агенту всё равно, что подставлено: он видит только `LLMProvider`.
Это и есть требование п.5/69 ТЗ — «любая бизнес-логика независима от LLM».

Если разделение нарушить (импорт `ollama` в агенте), перенос на RTX 3050
превратится в переписывание кода. Это главный риск проекта, поэтому
проверяется тестом `test_llm_provider.py::TestProtocolCompliance`.

## 3. Почему так, а не иначе

### Провайдеры выбираются фабрикой, а не `if` в агентах

Агент получает `LLMProvider`. Он не знает, MOCK это или REAL.
Фабрика — единственное место с ветвлением.

### Health-check различает REQUIRED и NOT REQUIRED

Ключевая проблема: на ноутбуке отсутствие Ollama — **норма**, а на машине
с RTX 3050 — **неисправимость**. Один и тот же отсутствующий компонент.

Поэтому `ComponentHealth` несёт поле `required`. Итоговый статус:

- `OK` — всё работает или штатно отсутствует;
- `DEGRADED` — обязательный для текущего режима компонент недоступен;
- `ERROR` — компонент упал с ошибкой.

Пример фактического вывода на ноутбуке:

```
Backend        OK
PostgreSQL     UNAVAILABLE   нет соединения с localhost:5432
Qdrant         MOCK          встроенный режим (memory)
LLM            MOCK          MockLLMProvider
Ollama         NOT REQUIRED  не требуется в режиме разработки
Embeddings     MOCK          MockEmbeddingProvider
GPU            NOT REQUIRED  режим разработки, GPU не требуется
```

### Деградация эмбеддингов вместо падения

Требование п.53 ТЗ: система обязана стартовать без модели эмбеддингов.

`get_healthy_embedding_provider()` при недоступности локальной модели
возвращает `HashEmbeddingProvider` и логирует предупреждение, пока
`EMBEDDINGS_OPTIONAL=true`. Если выставлено `false` — падает явно:
пользователь сам потребовал строгого режима.

### Настройки текут из приложения, а не из глобального .env

`create_app(settings)` кладёт настройки в `app.state.settings`, а роутеры
берут их через `Depends(settings_of)`.

Причина — реальный баг, пойманный тестом: `build_health()` читал
`get_settings()`, из-за чего проверка отражала прошлую конфигурацию.
Кэшированный `get_llm_provider()` усугублял это. Приложение, собранное
с нестандартной конфигурацией, обязано проверять именно её.

### HTTP-проверки в скриптах идут через Python

На машине разработки `curl.exe` и `Invoke-WebRequest` падают с
`SEC_E_INTERNAL_ERROR 0x80090304` (Schannel). Python `urllib` работает
нормально. Поэтому `scripts/lib.ps1` выполняет HTTP-запросы через
интерпретатор Python.

Это **не** обход качества: причина в сетевом стеке Windows, а не в коде
проекта. На машине с RTX 3050 скрипты будут работать через тот же путь.

### Почему SQLite, а не PostgreSQL (Фаза 3)

ТЗ требует PostgreSQL. На DEV-машине его установить нельзя: Docker
недоступен, на C: 1.2 GB, установка требует админа и перезагрузки.
Было три варианта: остановить работу до Фазы 4, заставить ставить БД
вручную или сделать слой переносимым.

Сделано третье. Слой данных не содержит ничего PostgreSQL-специфичного:
`Uuid` вместо `SERIAL`, `JSON` вместо `JSONB`, строки вместо нативных
`ENUM`. Один и тот же код работает на обоих диалектах.

Выбор БД — одна переменная:

```env
DATABASE_URL=   # пусто + дефолтные POSTGRES_* -> SQLite
DATABASE_URL=postgresql+asyncpg://courtdraft:courtdraft@localhost:5432/courtdraft
```

Что это даёт: Фазы 3–10 (модели, ingestion, агенты, Evidence Pack, Draft,
Verification) разрабатываются и тестируются сейчас, без внешних сервисов.
На RTX 3050 меняется только `.env`. Код не трогается (п.61).

Что проверяется явно, а не оставлено «на разберёмся при переносе»:

* **SQLite точность времени до секунды.** Две записи аудита в одной
  транзакции получают одинаковый `created_at`, порядок становится
  произвольным. Решение: у `audit_entries` первичный ключ —
  автоинкрементный `Integer`, а не UUID; сортировка по нему.
* **`lazy="selectin"` вне greenlet.** Обращение к связи сессии вне
  async-контекста даёт `MissingGreenlet`. В тестах связи считаются
  запросами, а не обращением к атрибуту.
* **`render_as_batch` в Alembic** для SQLite: обычный `ALTER COLUMN`
  SQLite не поддерживает.
* **PRAGMA foreign_keys=ON** для SQLite: без него `ON DELETE CASCADE`
  из моделей не работает, и удаление дела оставляет осиротевшие документы.
  Есть отдельный тест на каскад.

## 7. Метрики качества

Для юридического проекта BERTScore — **не** главная метрика (п.64).
Приоритет:

- `citation_precision` / `citation_recall` — точность ссылок;
- `unsupported_claim_rate` — доля утверждений без источника (главная);
- `verification_accuracy` — точность проверки;
- `factual_consistency` — согласованность с источниками;
- `retrieval Recall@5 / @10`, `MRR` — качество поиска.

Метрики считаются в MOCK-режиме: детерминированный провайдер даёт
воспроизводимые результаты, иначе измерялась бы случайность.
