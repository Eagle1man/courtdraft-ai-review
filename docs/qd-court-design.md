# QD-Court: архитектура и ограничения (Этапы 4–5 ТЗ)

Экспериментальный модуль поиска направлений анализа: пропущенные доводы,
доказательственные пробелы, противоречия. **Не является частью
обязательного пути подготовки судебного акта** и не может изменить исход,
суммы или детерминированные части (`RULES_BUILT_SECTIONS`).

## Происхождение идей

QD-Rec (SakanaAI, Apache-2.0) — архив item–hypothesis с novelty-first
admission, локальной конкуренцией и выбором бандитом; оригинал ходит в
OpenRouter. Перенесены только проверяемые архитектурные идеи:

| Идея QD-Rec | В QD-Court |
|---|---|
| архив гипотез | `ExplorationArchive`: один JSON на дело (`data/exploration/<case>.json`) |
| novelty-first admission | `admit()` + порог новизны по Жаккару токенов |
| локальная конкуренция | в пределах `question_id` живёт самая новизнная версия, старые — `SUPERSEDED` |
| отклонённые сохраняются | `REJECTED`/`UNSUPPORTED` остаются в архиве с причиной |
| explore / mutate | `DirectionProposer.explore()` / `.mutate()` |
| контекстный бандит | **не реализован** (ТЗ: сначала сравнить простой поиск и эволюционный архив) |

## Структура

```text
backend/app/exploration/
    models.py        Hypothesis (контракт), HypothesisStatus, HumanReviewStatus
    novelty.py       новизна по содержанию (Жаккар через app.rag.retrieval.tokenize)
    archive.py       архив, изоляция по делам, admit() с локальной конкуренцией
    proposer.py      Explore/Mutate на правилах проекта (без модели)
    verification.py  проверка оснований: источник существует, числа из материалов
    service.py       прогон с бюджетом, безопасный возврат
```

## Контракт гипотезы

`id`, `case_id`, `question_id`, `kind`, `text`, `sources`, `parent_ids`,
`model_version`, `novelty`, `checks`, `rejection_reason`, `status`,
`human_review`, `created_at/updated_at` — все поля из ТЗ присутствуют.
Гипотеза **никогда** не становится доказанным фактом: `SUPPORTED` означает
только «источники и числа подтверждены материалами»; оценку по существу
даёт человек (`human_review=PENDING` по умолчанию).

## Что проверяет `HypothesisVerifier`

1. Каждый источник гипотезы существует среди документов пакета — иначе
   `UNSUPPORTED` с причиной.
2. Каждое число гипотезы встречается в материалах — иначе `UNSUPPORTED`.
3. Статус `PROPOSED` не выдаётся наружу как результат: наружу идут только
   `SUPPORTED` (и то как направление для человека).

## Безопасность

- **Изоляция:** архив читается только по `case_id`; гипотезы чужих дел не
  используются (тест `test_cases_do_not_share_hypotheses`).
- **Нет записи в акт:** сервис не получает проект на вход и не возвращает
  текст резолютивной части; менять `RULES_BUILT_SECTIONS` физически нечем.
- **Лимиты:** `ExplorationBudget` — итерации, секунды, размер архива,
  порог новизны.
- **Отказ:** любое исключение → `fallback=True`, пустой результат, конвейер
  работает как раньше (тест `test_fallback_on_broken_archive`).
- **Без модели:** предлагающий — правила проекта; Ollama в окружении нет.
  Точка расширения одна (`DirectionProposer`), контракт гипотезы не меняется.

## Запуск

```powershell
backend\.venv\Scripts\python.exe scripts\qd_court_run.py   # прогон по 10 делам
backend\.venv\Scripts\python.exe -m pytest tests\test_exploration.py -q
```

## Чего модуль не делает

Не выносит вердиктов по существу, не считает «полезность» гипотезы без
разметки человека, не выбирает гипотезы автоматически (бандит не нужен:
направления показываются списком), не публикует и не сохраняет данные вне
каталога архива.
