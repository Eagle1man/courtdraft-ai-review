# Правовой режим данных проекта и история версий

Требование рецензента (п. 8): «История версий проекта и правок судьи фактически
отражает ход принятия решения. Нужно определить правовой режим этих данных: кто
имеет доступ, сколько хранятся, могут ли быть истребованы», и описать
соответствие продукта Национальной стратегии развития искусственного
интеллекта (Указ Президента РФ от 10.10.2019 № 490) и принципу независимости
судей.

**Статус документа.** Это рабочая памятка: здесь разделены *факты о коде*
(проверяемы по указанным файлам) и *вопросы правовой квалификации*. Документ
не является юридическим заключением. Каждый правовой вывод, который команда
не вправе делать сама, помечен `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`.

## 1. Какие данные создаёт система (факты по коду)

| Данные | Где хранятся | Что внутри |
|---|---|---|
| Версии проекта | `draft_versions` (`backend/app/models/entities.py`) | полный текст каждой версии (не diff), автор — `AI` / `SECRETARY` / `JUDGE`, комментарий, ссылки на источники, время создания |
| Результаты проверки | `verifications` | статус, замечания, счётчики |
| Журнал действий | `audit_entries` | `action`, `actor`, `case_id`, `details`; по правилу из `AuditRepository` **содержимое документов в журнал не попадает** |
| Материалы дела | каталог `data/cases/` | открытые файлы, без шифрования на диске |
| Индексы RAG | каталог индекса | в git не входят |

Правки человека сохраняются отдельной версией с автором
(`POST /api/drafts/{id}/versions`, `backend/app/api/routes/drafts.py`):
система не переписывает историю, а добавляет следующую редакцию — показать
акт «в том виде, в каком он был принят», — требование к юридической технике.

## 2. Кто имеет доступ (факт)

- Аутентификация и авторизация **не реализованы**: MVP рассчитан на локальную
  машину одного пользователя; выставление в сеть без контроля доступа
  недопустимо (`SECURITY.md`, «Известные ограничения MVP»).
- Фактический доступ = доступ к компьютеру и каталогу `data/`. Любой с таким
  доступом читает и материалы, и историю версий.
- Наружу данные не уходят: LLM и эмбеддинги локальные, CORS ограничен
  localhost (`SECURITY.md`).

**Вопросы специалисту:**

- Какой доступ к истории версий должен быть установлен регламентом суда
  (кто вправе читать, кто — править, какие роли вообще предусмотрены) —
  `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`.
- Реализация ролевого доступа (RBAC) и шифрование диска — не сделаны;
  перечень мер перед реальной эксплуатацией — в `SECURITY.md`.

## 3. Сроки хранения (факт)

Технических ограничений срока хранения в коде **нет**: записи версий,
проверок и аудита лежат в базе, пока их не удалят вручную. Автоочистки и TTL
не предусмотрены.

`ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`: какой срок хранения рабочих материалов
проекта и истории правок устанавливает регламент суда и подлежат ли они
уничтожению/архивированию по его правилам.

## 4. Тайна совещания судей (ст. 194 ГПК РФ) — вопрос специалисту

История версий и правок судьи по содержанию приближается к ходу принятия
решения, и рецензент указал на это прямо. Квалификация — не за командой
разработки:

- Относится ли история версий проекта к сведениям, составляющим тайну
  совещательной комнаты по ст. 194 ГПК РФ, либо это иные рабочие материалы —
  `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`.
- Порядок доступа к такой истории и возможность её истребования
  (вышестоящим судом, по ходатайству участников) —
  `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`.

Что система делает *сейчас* (технические факты, не правовая квалификация):

- история версий доступна только через локальный интерфейс/API на машине
  суда; выгрузки и публикации версий в продукте нет;
- система ничего не скрывает и не удаляет: история сохраняется полностью,
  правки различимы по автору (`AI`/`SECRETARY`/`JUDGE`);
- тексты материалов и индексы в git не входят, публикация проекта
  осуществляется только вручную и отдельным действием человека.

## 5. Независимость судей: человек в контуре, источник утверждения виден

Рецензент сформулировал два условия: «система не формирует выводов по делу
без контроля судьи и не скрывает источник каждого утверждения». Оба
проверяемы по коду:

**Вывод не появляется без человека:**

- генерация запускается только явным действием оператора
  (`POST /api/cases/{id}/draft`);
- у проекта статусы (`DRAFT` → `UNDER_REVIEW` → `VERIFIED` → `ACCEPTED`):
  принятие — отдельное действие с автором-человеком;
- вводная и резолютивная части собираются правилами без модели: суммы
  берутся из материалов, а не из рассуждений (`RULES_BUILT_SECTIONS`);
- неподтверждённое помечается в самом тексте
  `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`, а не выдаётся за вывод;
- проверка возвращает `REVIEW_REQUIRED`/`BLOCKED`, а не «готово»;
- публикацию на production агент не делает — это делает человек
  (также `AGENTS.md`).

**Источник каждого утверждения виден:**

- у каждой версии — свой список `citations`;
- под каждым разделом проекта — источники (или честная пометка
  «источник не указан»);
- замечания проверки привязаны к разделам и читаются рядом с абзацем;
- счётчик `unsupported_claims` показывает, сколько утверждений
  подтвердить не удалось, — он не обнуляется молча.

## 6. Национальная стратегия развития ИИ (Указ Президента РФ от 10.10.2019 № 490)

Описание соответствия *проектных решений* принципам Национальной стратегии,
а не сертификация продукта:

1. **Человек в контуре принятия решения.** Система готовит проект; решение
   принимает судья — раздел 5 выше.
2. **Прозрачность и объяснимость.** Каждое утверждение либо имеет ссылку на
   материал дела, либо помечено как требующее проверки; «чёрного ящика» без
   источника продукт не создаёт.
3. **Защита данных.** Обработка локальная: материалы не покидают машину,
   облачные LLM и embedding-сервисы не используются (`SECURITY.md`).
4. **Незамещение судьи.** Продукт не выносит судебных актов и не публикует
   их; статусы и пометки устроены так, что незаконченный результат нельзя
   выдать за готовый.

`ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`: официальная оценка соответствия продукта
Национальной стратегии и порядок такого описания при представлении продукта
в суде.

## 7. Что не сделано (честный список)

Перед применением на реальных делах (`SECURITY.md`):

1. аутентификация и авторизация (RBAC) — нет;
2. шифрование хранилища — нет;
3. ограничение сроков хранения — нет;
4. правовая квалификация истории версий (ст. 194 ГПК), сроки хранения и
   основания истребования — `ТРЕБУЕТ ПРОВЕРКИ СПЕЦИАЛИСТОМ`;
5. обезличивание PII основано на регулярных выражениях и не заменяет
   специализированную обработку.
